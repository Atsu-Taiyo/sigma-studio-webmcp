# 本文編集のカーソル挙動仕様

2026年8月27日改訂 (PR #534「キャレット位置の権威モデル一本化」)。ページを跨ぐブロックが
複数の編集面に描かれる前提へ合わせ、§3 とページ・段組みの節、実装差分の一覧を書き直した。

## 目的

Sigma Studio の本文編集で、改行、折り返し、ページ送り、段組み変更、ブロック分割などが起きても、カーソルが意図しないブロック末尾や編集領域の最下部へ移動しないようにする。

操作感の基準は Microsoft Word とする。ただし、Word の内部実装や画面を再現するのではなく、ユーザーから見える次の性質を揃える。

- 入力した直後の位置にカーソルが残る
- クリックした行の、クリック位置に最も近い文字間へカーソルが置かれる
- 上下移動では、可能な限り同じ横位置を保つ
- 改行後は新しく作られた行または段落の先頭へ移る
- 自動折り返しやページ再配置だけでは、文書中の論理位置が変わらない
- 選択範囲を置換・削除した後は、置換・削除が始まった位置へ残る

参考:

- [Microsoft Support: Keyboard shortcuts in Word](https://support.microsoft.com/en-us/accessibility/word/keyboard-shortcuts-in-word)
- [Microsoft Support: Insert a page break in Word](https://support.microsoft.com/en-us/word/insert-a-page-break-in-word)

## 適用範囲

この仕様は、SigmaDoc の本文フローを編集する次の領域へ適用する。

- 通常の段落と見出し
- 問題の導入文、問題文、コメント、解答
- 箇条書き、番号付きリスト
- 本文フロー内の箱
- ヘッダー、フッターなど、本文と同じリッチテキスト編集を行う領域
- 本文中のインライン数式や囲み文字の前後
- ページおよび段をまたぐ連続本文

図形、グラフ、画像などのオーバーレイ選択は対象外とする。ただし、オーバーレイ操作から本文編集へ戻る際のカーソル復帰は本仕様に従う。

## 用語

### カーソル

文字を入力する位置を示す、選択範囲が閉じた状態を指す。技術的にはキャレットに相当するが、製品内の説明では「カーソル」と呼ぶ。

### 選択範囲

開始位置と終了位置が異なる文字範囲を指す。

### 論理位置

画面上の座標ではなく、SigmaDoc 本文中の編集位置を指す。最低限、次の情報で特定できるものとする。

```ts
type CaretAddress = {
  blockId: string;
  offset: number;
  affinity: "before" | "after";
  kind: "text" | "node";
};

type CaretBookmark = {
  anchor: CaretAddress;
  head: CaretAddress;
  preferredX: number | null;
};
```

- `blockId`: カーソルを含む意味上の本文ブロック。**最も内側の、id を持つブロック**を指す
- `offset`: そのブロック内の文字・インライン要素を含む編集オフセット
- `affinity`: 改行や境界の前後どちら側に属するか
- `kind`: `"node"` は区切り線・箱・段組みセクションのように**ノードそのもの**を選んでいる状態
- `preferredX`: 上下移動中に維持したい画面上の横位置。持たないときは `null`

実装は `apps/desktop/src/features/text-editing/model/caret-address.ts` と `caret-bookmark.ts`。
ProseMirror の position や DOM Range を一時的に利用してよい。ただし、React の再描画、Tiptap 文書の再構築、ページ分割表示をまたいで保持する基準にはしない。

**`offset` の意味は出所で異なる。** ProseMirror の位置から作る場合は「最も内側の id を持つブロックの中での位置」、SigmaDoc から作る場合は「平坦化した文字数」である。前者はコンテナの途中でも往復が成立するが、後者はコンテナ id に載せると別の場所を指す。だから SigmaDoc から作る経路 (`caretAddressAtBlockStart` / `caretAddressAtBlockEnd`) は必ず葉ブロックまで降りる。

### 表示行と段落

- 表示行: 横幅による自動折り返しを含む、画面上の1行
- 段落: Enter で分割される SigmaDoc の意味上の本文ブロック
- 手動改行: Shift+Enter で段落内に作る改行

自動折り返しは文書構造を変えない。段落改行と手動改行は文書構造上の編集である。

## 基本原則

### 1. 編集操作の前後で論理位置を対応させる

カーソルは、編集前の論理位置を編集トランザクションによって写像した位置へ移す。再描画後に「選択中のブロックの末尾」「最後のブロック」「DOM上で最後に見つかった編集要素」へ置き直してはならない。

### 2. レイアウト変更はカーソル位置を変更しない

次の変化は表示上の再配置であり、カーソルの論理位置を変更しない。

- 文字入力に伴う自動折り返し
- ページ追加または削除
- 前後の文章量の変化によるページ移動
- 段組みへの流し直し
- 用紙サイズ、余白、ズームの変更
- フォント、文字サイズ、行間の変更
- ページ分割用スペーサーやページ断片の再生成

カーソルが画面外へ移動した場合は、論理位置を変えず、その位置が確認できる最小限のスクロールを行う。

### 3. カーソルを所有する編集面は常に1つ

ページや段を跨ぐブロックは、正本 (`clip-path` で1断片目だけを見せる本文フロー内のノード) と、断片ごとの複製 (`translateY` で切り出す独立した ProseMirror) という **N+1個の編集面**に描かれる。どの面も同じ SigmaDoc id と同じ本文を持つ。

**断片も編集可能な面である。** 断片を読み取り専用にして自前でカーソルを描く案は採らない。IME の変換候補ウィンドウの表示位置は OS がネイティブの選択矩形から決めるため、読み取り専用にすると変換候補が見えない位置に出るからである。

正本は SigmaDoc JSON であり、論理位置の権威は `CaretAddress` ただ1つとする。そのうえで:

- **DOM フォーカスと DOM 選択を持ってよいのは、その論理位置を実際に画面へ見せている面ただ1つ**とする。
- どの面が見せているかは、断片テーブル (各断片が見せるブロック内の帯) とブロック内の縦位置から一意に決まる。判定は `apps/desktop/src/features/rendering/core/caret-placement.ts` の純関数が持ち、配送は `apps/desktop/src/components/editor/text-flow/caret-router.ts` が行う。
- 論理選択は複数の面が持ちうる (断片を跨ぐ範囲選択の帯は各面が自分の担当ぶんを描く)。**DOM 選択を持つのは1面だけ**という点が制約である。
- 計測用DOM・プレビュー・印刷ステージの面へフォーカスや選択を移してはならない。

### 4. 明示的な操作だけが位置を大きく変える

クリック、矢印キー、Home / End、検索結果への移動、ブロック選択、ページ移動など、ユーザーが移動を意図した操作ではカーソルを移してよい。

入力、保存、自動保存、同期、ページ再計算、ツールバー操作だけを理由に、別ブロックや文書末尾へ移してはならない。

### 5. フォーカス復帰とカーソル移動を分ける

ツールバーやポップオーバーから本文へフォーカスを戻す場合は、直前のカーソルまたは選択範囲を復元する。フォーカスを戻すこと自体を、ブロック末尾への移動として扱わない。

## 操作別の期待動作

### クリック

| 操作 | 期待動作 |
| --- | --- |
| 文字の左半分をクリック | その文字の前へ置く |
| 文字の右半分をクリック | その文字の後へ置く |
| 表示行の文字より右側をクリック | その表示行の末尾へ置く |
| 表示行の先頭より左側をクリック | その表示行の先頭へ置く |
| 段落内の上下余白をクリック | クリック位置に最も近い表示行の先頭または末尾へ置く |
| 空の段落をクリック | その空段落の先頭へ置く |
| ページ上の本文外余白をクリック | 本文のカーソルを解除する。別ブロック末尾へ移さない |
| 本文を覆う操作用オーバーレイ越しにクリック | 最終的な画面座標に最も近い本文位置へ引き渡す |

同じ `contenteditable` 内であっても、クリックした行と無関係なブロック末尾へ丸めてはならない。
行・ブロック選択専用のガターはこの規則の対象外とし、通常の本文クリック領域とヒット領域を分ける。

### 文字入力

- 入力した文字の直後へ移る。
- 文字入力によって表示行が折り返されても、入力した文字の直後という論理位置を維持する。
- IME変換中は、DOMやTiptap文書を再構築して変換中のカーソルを移動させない。
- IME確定後は、確定した文字列の直後へ置く。
- 入力によって次のページまたは段へ流れた場合も、入力位置に追従する。

### Enter: 新しい段落

通常の本文で Enter を押した場合は、現在の段落をカーソル位置で分割する。

```text
操作前:  ABC|DEF
操作後:  ABC
          |DEF
```

- カーソルは分割後の後半段落の先頭へ置く。
- 段落末尾で Enter を押した場合は、直後に空段落を作り、その先頭へ置く。
- 段落先頭で Enter を押した場合は、直前に空段落を作る。カーソルは元の内容がある後半段落の先頭に残す。
- 選択範囲がある場合は、まず選択範囲を削除してから、その位置で段落を分割する。
- 分割後のブロック種別や書式継承は各ブロックの仕様に従うが、カーソルは常に編集を続ける側の先頭へ置く。
- Enter を契機にブロックIDが増減しても、再同期処理で末尾へ移動させない。

リストなど、空項目で Enter を押すと構造を終了する編集領域では、終了後に作られた通常段落の先頭へ置く。

### Shift+Enter: 段落内の手動改行

```text
操作前:  ABC|DEF
操作後:  ABC↵
          |DEF
```

- 同じ段落内に手動改行を挿入する。
- カーソルは改行の直後、次の表示行の先頭へ置く。
- 自動折り返しとは区別する。
- ページや段の境界に重なっても、次の論理文字位置へ置く。

### Backspace と Delete

| 操作 | 期待動作 |
| --- | --- |
| 通常位置で Backspace | 直前の文字またはインライン要素を削除し、その位置へ置く |
| 通常位置で Delete | 直後の文字またはインライン要素を削除し、元の位置を維持する |
| 段落先頭で Backspace | 前段落と結合し、結合点へ置く |
| 段落末尾で Delete | 次段落と結合し、結合点へ置く |
| 選択範囲を削除 | 選択範囲の開始位置へ置く |
| 空ブロックを削除 | 論理順で隣接する編集可能位置へ置く |

境界削除が問題エリア、箱、段組みなどの構造境界をまたげない場合は、削除を行わず現在位置を維持する。拒否した操作の代わりに別ブロックへ移動してはならない。

### 左右矢印

- 左右矢印は、論理順で1文字または1インライン要素ずつ移動する。
- 自動折り返し位置では、左右の論理文字位置へ連続して移動する。
- インライン数式や囲み文字は1つのインライン要素として境界を越える。
- インライン数式の編集モードへ入る操作と、本文カーソルが数式の前後を移動する操作を混同しない。
- 段落境界では、前段落末尾と次段落先頭を連続した位置として移動する。

### 上下矢印

上下矢印は Word と同様に、現在の表示上の横位置をできるだけ維持して前後の表示行へ移動する。

```text
長い行:  あいうえおかきくけこ|さしすせそ
短い行:  あいうえお|
長い行:  あいうえおかきくけこ|さしすせそ
```

- 短い行ではその行の最も近い位置へ一時的に置く。
- さらに同じ方向へ移動して長い行へ入ったときは、元の横位置 `preferredX` を復元する。
- ページ境界、段境界、問題エリア境界を越えても、論理順で隣接する表示行へ移動する。
- ページの最下部やブロックの最下部へ一律に丸めない。
- 左右移動、Home / End、クリック、文字入力など、横位置を明示する操作を行った時点で `preferredX` を新しい位置へ更新する。

### Home / End と修飾キー

プラットフォーム標準の Word 操作へ合わせる。

| 操作 | 期待動作 |
| --- | --- |
| Home | 現在の表示行の先頭へ移動 |
| End | 現在の表示行の末尾へ移動 |
| Mod+Up | 現在または前の段落先頭へ移動 |
| Mod+Down | 現在または次の段落末尾へ移動 |
| Mod+Home | 文書先頭へ移動 |
| Mod+End | 文書末尾へ移動 |
| Shiftを併用 | 同じ移動規則で選択範囲を拡張 |

`Mod` は Windows では Ctrl、macOS ではアプリとOSの標準操作に対応するキーを指す。ブラウザ既定とデスクトップ版の操作が競合する場合は、Electronデスクトップ版で Word に近い編集操作を優先する。

### 選択範囲の置換

- 文字入力では選択範囲を入力内容で置換し、入力内容の直後へ置く。
- Enter では選択範囲を削除し、その位置で段落を分割する。
- Shift+Enter では選択範囲を削除し、その位置へ手動改行を挿入する。
- 貼り付けでは貼り付けた内容の直後へ置く。
- Undo / Redo では、文書内容とともに操作時のカーソルまたは選択範囲を復元する。

### 手動改ページ・改段

手動改ページ・改段は「カーソル位置より後ろの内容を次のページまたは段から始める」操作として扱う。

```text
操作前:  ABC|DEF
操作後:  ABC
          --- 改ページまたは改段 ---
          |DEF
```

- ブロック途中ではブロックを分割し、後半の先頭へ置く。
- ブロック末尾では、次のブロックの先頭へ置く。次のブロックがなければ空段落を作り、その先頭へ置く。
- ブロック先頭では、その位置から次ページ・次段を開始し、同じ内容の先頭へ置く。
- 改ページの解除では、対象内容の先頭を維持する。
- レイアウト確定後に同じ内容が別ページへ移っても、カーソルを元ページの末尾へ残さない。

### 書式変更とツールバー操作

- 太字、斜体、下線、色、文字サイズ、行間、段落種別などを変更しても、カーソルまたは選択範囲を維持する。
- 選択範囲がない文字書式は、現在のカーソルに保存書式として適用し、次の入力へ反映する。
- ツールバーへ一時的にフォーカスが移っても、本文へ戻る際に直前の位置を復元する。
- 書式変更による折り返しやページ再計算は、論理位置を変えない。

### インライン数式

- 本文カーソルはインライン数式の直前または直後に置ける。
- 数式を挿入した後は、仕様上「数式の編集を開始する」場合を除き、数式の直後へ置く。
- 数式編集を確定した後は、元の本文内で数式の直後へ戻す。
- 数式編集をキャンセルした後は、開始前のカーソルまたは選択範囲へ戻す。
- 数式内カーソルと本文カーソルを別の状態として保持し、一方の更新で他方を文書末尾へ移さない。

### フォーカス喪失と復帰

| 状況 | 復帰位置 |
| --- | --- |
| ツールバー操作後 | 操作前のカーソルまたは選択範囲 |
| ポップオーバーを閉じた後 | ポップオーバーを開く前の位置 |
| 数式編集確定後 | 対象数式の直後 |
| Undo / Redo 後 | 履歴に保存された位置 |
| アプリが一時的に非アクティブになった後 | 最後に編集していた位置 |
| 別ブロックを明示的に選択した後 | 選択したブロック内の指定位置。指定がなければ先頭 |

復帰対象のブロックが削除済みの場合は、削除前の論理順に最も近い編集可能位置を選ぶ。無条件に文書末尾へ移動しない。

## 再描画・同期時の規則

### Tiptap 文書の更新

SigmaDoc から Tiptap 文書を再構築する必要がある場合は、更新前に論理位置を保存し、更新トランザクションによって新しい位置へ写像してから復元する。

優先順位は次のとおりとする。

1. 同じ `blockId` と写像後の `offset`
2. 同じ `blockId` 内で最も近い有効な `offset`
3. 論理順で直前のブロック末尾
4. 論理順で直後のブロック先頭
5. 文書内に編集可能位置がない場合のみ、選択なし

「現在選択されているブロックの末尾」や「最後のブロック」は復元規則の既定値にしない。

### SigmaDoc への書き戻し

Tiptap から SigmaDoc へ書き戻す際、ブロックIDの正規化や新規採番が発生しても、分割前後の対応関係を編集トランザクション内で保持する。

カーソル復元のために Tiptap JSON や DOM Range を SigmaDoc へ保存してはならない。カーソルは編集セッション状態であり、SigmaDoc の永続データではない。

### ページ・段組み表示

- ページ分割用の空きは、編集可能な段落の大きな `margin` ではなく、カーソル対象外の装飾またはスペーサーとして表現する。
- 断片は編集面なので、クリックはその面が自分で受ける (正本へ座標変換して引き渡すことはしない)。
- 正本と断片の両方に同じ **DOM 選択**を作らない。論理選択は全面が持ちうる。
- 断片の切り出し窓は `overflow: clip` とし、`scrollTop` が 0 以外になれないようにする。`overflow: hidden` はスクロールコンテナを作るため、ブラウザ自身の caret-into-view や ProseMirror の既定のスクロール追従がそこを動かし、断片が恒久的にずれる。
- カーソル追従で動かしてよいのは紙面のスクローラー (`.editor-canvas`) だけとする。`translateY` で上へ押し出された内容は `scrollTop` では戻せない。
- レイアウト計測中も、正本の編集面をアンマウントまたは再生成しないことを優先する。

### 外部更新・AI編集

> **未実装 (本編スコープ外 / follow-up)。** 以下は目標の記述であり、2026年8月27日時点で実装されていない。

- カーソルより前への挿入: 同じ内容を指すようにオフセットを進める
- カーソルより後への挿入: 位置を維持する
- カーソルを含む範囲の置換: 置換後範囲の末尾または操作で明示された位置へ置く
- カーソルを含むブロックの削除: 削除位置に最も近い編集可能位置へ置く

外部更新を知らせるために本文フォーカスを奪わない。

## 現行実装との責務対応

本仕様を実装する場合の主な責務は次のとおり。

| 責務 | 主な場所 |
| --- | --- |
| Tiptap selection、キー入力、本文ブロックとの位置対応 | `apps/desktop/src/components/editor/TextFlowEditor.tsx` |

## 実装状況と、実装前の Sigma Studio との差分

2026年7月30日に確認した実装前の差分と、本仕様に基づく対応状況を示す。

| 実装前の差分 | 対応 |

### 実装前の実行確認

### 実行確認で再現した差分

#### 1. 40ブロック境界の Enter では、カーソルが分割前側へ残る

通常の短い本文では、段落中央の Enter は本仕様どおり動作する。

```text
操作前:  段落|0
操作後:  段落
          |0
```

一方、かつての実装は連続する本文を「先頭から数えて40ブロックごと」に `TextFlowEditor` へ分割していた。40番目のブロック中央で Enter を押し、そのブロック分割によって後続ブロックが次の `TextFlowEditor` へ移る場合は、次の状態になった。

```text
期待:  段落3
       |9

現行:  段落3|
       9
```

本文の保存結果と表示ブロック数は正しく、重複ブロックも発生しなかったが、カーソルだけが分割後の後半段落へ追従していない。

原因となる境界は次の組み合わせにあった。

- `TEXT_FLOW_BLOCKS_PER_RENDER_UNIT_TARGET = 40` (当時の名前は `MAX_...`。件数そのものが境界だった)
- `buildRenderUnits(...)` による本文フローの複数 `TextFlowEditor` 化
- ブロックID列が変化したときの `editor.commands.setContent(...)`
- 旧Editorと新Editorをまたぐ論理カーソル位置の引き渡しがないこと

**現在の実装**: 分割の境界は「先頭から数えた件数」ではなく**ブロックIDで固定**している (`page-canvas/text-run-chunking.ts`)。ブロックを1つ挿入・削除しても既存の境界は動かず、上限 (目安の2倍) を超えたチャンクだけがその場で切り直され、下限 (目安の1/4) を割ったチャンクだけが隣と併合される。したがって Enter や貼り付けで後続ブロックが「次の `TextFlowEditor` へずれる」ことは起きなくなり、上記の再現手順ではカーソルは分割後の後半段落に付いたままになる (実測: 本文1500ブロックの文書で Enter×4 の数式ノードビュー再マウントが 196 → 1、keydown p50 が 24ms → 16ms。`InlineMathView.mount` カウンタは本番ビルドの perf-probe で読む値で、開発ビルドは StrictMode により2倍に数える)。境界そのものが変わる場合 (チャンクの切り直し・併合) には従来どおり `setContent` 経路を通るため、下の「引き継ぎ」の仕様は引き続き必要。

境界の決め方には次の2つの契約がある。破ると「編集していないのに次の描画で境界が動く」= 作り直しが1回起きる。

- **不動点**: ある描画の出力から作った境界を渡し直しても結果は変わらない。初回だけ併合を飛ばすといった特別扱いを入れると崩れる (45ブロックが 40+5 → 45 に変わり、開いて最初の1打鍵で2つ目のユニットが破棄される)。
- **実描画のユニットが唯一の出典**: 境界は前回の描画から引き継ぐので、ブロック列から組み直したユニットは実描画と一致しない。右クリックメニューの改ページ/改段の対象解決のように後からユニットを必要とする経路は、**描画中の `units` を受け取る** (`getColumnBreakBeforeBlockIdForContextMenu`)。

境界は `PageCanvasEditor` が ref で持ち回るが、`docId` を添えて**同じ文書のときだけ**引き継ぐ。印刷プレビューのステージは同じインスタンスで別の教材を描くことがあり、テンプレート複製の教材どうしはブロックIDが一致しうるため。なお画面側は編集履歴に応じて境界が動くので、同じ文書でも画面と印刷ステージのユニット分割は一致しないことがある (ページ割りはトップレベルブロック単位で歩くため幾何には効かない)。

#### 2. Undo 後に、操作前のカーソル位置へ戻らない

1つ目の段落中央へ文字を入力してUndoしたところ、本文は元に戻ったが、カーソルは2つ目の段落末尾へ移動した。

```text
操作前:  段落|0
入力後:  段落X|0

期待するUndo後:
         段落|0

現行のUndo後:
         段落0
         段落1|
```

現行の文書履歴はSigmaDocと選択中のブロックIDを保持するが、ブロック内オフセット、選択範囲、境界の前後関係は保持しない。Undo / Redo の `historyRevision` 更新後はTiptap文書全体を `setContent(...)` しており、操作前のカーソルを復元する情報が不足している。

#### 3. 問題の導入文では Enter が何も行わない

問題の導入文は `singleBlock` の `TextFlowEditor` として描画され、Enter は `preventDefault()` されたうえで処理済みになる。

- 本仕様: Enterで段落を分割し、後半段落の先頭へ移る
- 現行: 本文もカーソル位置も変化しない

これは偶発的なカーソル移動ではなく、現行コードで明示された単一ブロック制約である。導入文でもWord相当の複数段落編集を認めるか、導入文だけを仕様上の例外にするか、製品判断が必要になる。

### コード上、仕様を満たす保証がない差分

#### 4. 論理カーソル位置の共通表現がない → **解消済み**

`CaretAddress` (`features/text-editing/model/caret-address.ts` / `caret-bookmark.ts`) が唯一の表現になった。`blockId` は必ず葉ブロック、`affinity` と `kind` を持ち、選択は `preferredX` を載せる。旧 `TextFlowSelectionPoint` は残していない。

区切り線などトップレベルの atom を選んだ状態も `kind: "node"` で表せる (以前は必ず `null` になり、選択中の undo / redo でカーソルを失っていた)。

#### 5. `setContent(...)` 前後のカーソル写像がない → **実装済み**

`setTextFlowContentPreservingSelection` (`TextFlowEditor.tsx`) が `setContent` の前に `CaretBookmark` を取り、後で復元する。復元は「選択の適用」と「DOM フォーカスの取得」を分けてあり、フォーカスを取るのは§3の意味で**その位置を見せている面だけ**である。

AI編集・外部更新による位置写像だけは別で、こちらは未実装 (「外部更新・AI編集」の節を参照)。

#### 6. 上下移動の `preferredX` をアプリ側で保持していない → **解消済み**

上下移動は `caret-router.ts` の `moveCaretVertically` が**先回りして**行き先の面を決め、`preferredX` を行き先へ引き継ぐ。**面をまたぐときだけ介入**し、同じ面の中の移動はブラウザと ProseMirror に任せる (折り返し・双方向テキスト・数式ノードビューの中まで自前で持たない)。

行き先の面は断片テーブルから決めるので、断片の境界がテキストブロックの境界と一致しなくても正しく渡る。文書順を持たない面 (素材ダイアログ・ヘッダ/フッタ) は行き先の候補にしない。

**残っている差分**: Shift + 上下による選択拡張が断片を跨ぐ場合と、`Home` / `End` / `Mod+Up` / `Mod+Down` の断片跨ぎは未対応 (follow-up)。

#### 7. 選択範囲がない文字サイズ・色などは、カーソル以後ではなくブロック全体へ適用される

太字、斜体、下線、囲み文字は、選択範囲がない場合にカーソル位置の保存書式として働き、次に入力する文字だけへ反映される。

一方、文字サイズ、文字色、フォントなどは、選択範囲がない場合に選択中ブロック全体へ適用する現行仕様が残っている。

- 本仕様: カーソル位置に保存書式を設定し、次の入力へ反映する
- 現行: 選択中の本文ブロック全体を変更する

これは `text-format-controller.ts` でもWord / Google Docsと異なる既存フローとして明示されている。

#### 8. 一部のフォーカス復帰はブロック先頭・末尾までしか表現できない → **解消済み**

`caretAddressAtBlockEdge` がブロックの端から `CaretAddress` を作り、入れ子ブロック (箱 / 引用 / 段組み / リスト) では**葉ブロックまで降りる**。境界削除・手動改ページの復帰はこの住所をルーターへ渡すので、見えている面へ戻る。

あわせて、焦点を戻すときに `selectNodeContents` でブロック全体を選択したまま残す経路を廃止した。指定が無ければ**先頭へ畳む**。全選択のまま残すと、次に打った文字がブロックごと置き換わる (「回帰として禁止する状態」に該当した)。

#### 9. オーバーレイ越しに input / textarea へ戻る場合は常に末尾へ移る

オーバーレイから `contenteditable` へクリックを引き渡す場合は、画面座標から最も近い文字位置を求めている。

一方、引き渡し先が `input` または `textarea` の場合はクリック座標を使わず、常に `value.length` へカーソルを置く。この経路では、クリックした位置ではなく入力欄末尾へ移動する。

### 現行ですでに一致している主な動作

次の動作は、実行確認または既存E2Eで本仕様と一致している。

- 通常段落の中央でEnterを押すと、後半段落の先頭へ移る
- 通常段落の末尾でEnterを押すと、新しい空段落の先頭へ移る
- Shift+Enterでは同じ段落内へ手動改行を挿入し、その直後へ移る
- ページ増加後も本文の重複保存は発生しない
- ページ先頭の空きは編集段落の巨大なmarginではなく、カーソル対象外のスペーサーで表現される
- キャレットを所有するのは、その論理位置を実際に見せている面ただ1つである
- 問題文、コメント、解答のクリックは対象エリアへフォーカスする
- 選択範囲へ文字サイズやフォントを適用した後も、その選択範囲を維持する
- 選択範囲がない太字、斜体、下線、囲み文字は、次に入力する文字へだけ反映される
- 段落境界のBackspace / Deleteは、解決後の隣接ブロック先頭または末尾へフォーカス要求を出す

### 優先度

現在報告されている「改行時にブロックの一番下へ移る」症状へ直接対応する優先順位は次のとおり。

1. 40ブロック境界をまたぐEnter後のカーソル引き渡し
2. `setContent(...)` 前後の論理位置保存・写像・復元
3. Undo / Redo履歴へのカーソル・選択範囲の追加
4. 上下移動用 `preferredX` のEditor境界をまたぐ維持
5. 導入文、文字書式、改ページ解除など意図的な現行差分の製品判断

## 受け入れ基準

### 必須シナリオ

1. 段落中央で Enter を押すと、後半段落の先頭にカーソルがある。
2. 段落末尾で Enter を10回続けても、毎回新しい空段落の先頭にカーソルがある。
3. Enter によってページが1枚増えても、カーソルは最後に作った段落の先頭にある。
4. 1文字入力した結果、段落が次ページへ押し出されても、その文字の直後にカーソルがある。
5. ページ先頭へ移動した段落をクリックすると、その表示行のクリック位置にカーソルが置かれる。
6. 表示行の右側余白をクリックしても、同じ行の末尾に置かれ、ブロック全体の末尾へ飛ばない。
7. 上下矢印で短い行を挟んで移動すると、長い行で元の横位置へ戻る。
8. 段落先頭の Backspace で前段落と結合した後、結合点にカーソルがある。
9. 選択範囲を文字入力で置換した後、入力文字列の直後にカーソルがある。
10. ツールバーで書式を変更した後、本文へ戻って入力すると元の位置へ文字が入る。
11. 手動改ページを段落中央へ入れると、次ページに移った後半段落の先頭にカーソルがある。
12. 自動保存、ページ再計算、ズーム変更だけではカーソル位置が変わらない。
13. インライン数式編集の確定後、本文カーソルが対象数式の直後へ戻る。
14. IME変換中にページ再計算が発生しても、未確定文字列とカーソルが別位置へ移らない。
15. Undo / Redo で本文とカーソル位置が同時に復元される。

### 回帰として禁止する状態

- Enter 後に同じブロックの最下部へ移る
- Enter 後に文書中の最後のブロックへ移る
- ページ再計算後に先頭または末尾へ移る
- **その論理位置を見せていない面**がフォーカスを持つ
- **同時に2つ以上の面が DOM 選択を持つ**
- **ページ断片の viewport が 0 以外の `scrollTop` を持つ**
- **焦点を戻した直後にブロック全体が選択されたまま残る** (次の入力がブロックごと置換される)
- クリックした行ではなく、`contenteditable` 全体の末尾へ移る
- ツールバー操作後に選択範囲が失われる
- IME変換中に確定またはカーソル移動が起きる
- カーソル復元のためにSigmaDocへTiptap固有状態を保存する

## テスト方針

### 単体テスト

ReactやDOMへ依存しない次の規則を `features/text-editing` で検証する。

- ブロック分割前後の論理位置写像
- ブロック結合前後の論理位置写像
- 選択範囲削除・置換後の位置
- 手動改ページ・改段後の `focusBlockId` とオフセット
- 対象ブロック削除時の近傍位置解決

### E2Eテスト

実際のブラウザselection、ProseMirror、ページ再計算を含む挙動は Playwright で検証する。

- `apps/desktop/tests/e2e/continuous-pagination.spec.ts`
- 本仕様専用の `apps/desktop/tests/e2e/caret-behavior.spec.ts`
- インライン数式境界を扱う既存テスト
- 問題エリア、箱、段組みを扱う既存テスト

テストでは「対象ブロックが選択中である」だけでなく、次を確認する。確認は共通ヘルパ
`apps/desktop/tests/e2e/caret-surface.ts` の `readCaretSurface` が返す値で行う。
**`blockId` と `textContent` だけを見るヘルパでは、キャレットが間違ったコピーにあっても緑になる** —
正本と断片の複製は同じ値を持つからである。

| 仕様書の要求 | ヘルパが返す値 |
| --- | --- |
| `window.getSelection()?.isCollapsed === true` | `collapsed` |
| selection の `anchorNode` がどの面にあるか | `selectionSurface` (`source` / `replica` + `fragmentIndex` / `outside`) |
| `blockId` が期待するブロックと一致する | `blockId` |
| ブロック内オフセットが期待値と一致する | `offset` |
| カーソル矩形のx座標が許容誤差内にある | 上下移動の往復で `offset` が戻ることで代替 (`preferredX` は内部状態で、DOM からは読めない) |
| 同じ本文を持つ他の面がselectionを所有していない | `activeSurface` と `selectionSurface` が一致すること + `spanSurfaceCount` |
| キャレットが実際に見えている | `caretVisible` (キャレット矩形の縦中点が、その面の可視帯の半開区間に入るか) |
| ページ断片がずれていない | `maxFragmentScrollTop === 0` |

加えて、復元1回あたりのフォーカス移動回数は `countFocusIn` で数える (断片がN個あっても1回であること)。

## 完了条件

この仕様の完了は、特定の不具合1件だけが直ることではない。必須シナリオを自動テストで満たし、本文の再描画・同期・ページ計算に関わる処理が「現在ブロック末尾へのフォールバック」を通常経路として使わなくなった状態を完了とする。

Word と差が残る場合は、差を暗黙の挙動にせず、この文書へ例外、その理由、対象操作を追記する。
